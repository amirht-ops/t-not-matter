# ADR-008

Title:

Delegation Feature within AuthorizationService

Status:

Accepted

---

# Context

The README references a 6th bounded context "Delegation Service" for temporary permission transfer. However:

1. No delegation code exists — zero aggregates, zero events, zero consumers, zero endpoints
2. ADR-001 lists 4 services (Identity, Authorization, Policy, Audit) — Delegation was never formally approved
3. A detailed specification exists at `docs/specs/delegation-specification.md`
4. A complete architectural blueprint exists in `Addendum_A_Deep_Dive_Architectural_Resolutions.md`
5. `AuthorizationDecisionService` Step 5 already reads `delegated_permissions` from context (but no caller populates it)
6. `DelegationDenied` reason code exists but is never produced
7. `AuditCategory.Delegation` enum exists but is never used

The question is: implement as 6th bounded context or integrate into AuthorizationService?

---

# Decision

Implement delegation as a **feature within AuthorizationService**, not as a separate bounded context.

---

# Rationale

### 1. Delegation IS Authorization

Delegation is fundamentally about "who can do what" — the same question AuthorizationService answers. The `AuthorizationDecisionService` pipeline already has Step 5 (Delegation Resolution) designed for this.

### 2. Data Coupling is Inevitable

Delegation requires:
- `RoleAssignment` aggregate (already exists in AuthorizationService)
- `PermissionGrant` aggregate (already exists in AuthorizationService)
- `EffectivePermissionResolver` (already exists, already merges delegated permissions)

Creating a separate service would require cross-service queries or eventual consistency for data that lives together naturally.

### 3. Simpler Architecture

Separate bounded context requires:
- 6th database schema
- Cross-service integration events
- Additional infrastructure (6th API, 6th consumer, 6th Outbox)
- Complexity without demonstrated benefit

### 4. Specification Constraints Align

The delegation specification requires:
- "Cannot exceed owner permissions" → requires access to full permission graph (AuthorizationService)
- "Approval requirement for sensitive permissions" → requires permission classification (AuthorizationService)
- "Audit trail" → already handled by AuditBehavior + AuditService consumers
- "Automatic expiration" → background worker within AuthorizationService

### 5. Consistency with Existing Patterns

`RoleAssignment` already has `AssignedAtUtc` and `RevokedAtUtc`. Adding `ExpiresAt` (delegation expiry) is a natural extension.

# Implementation Plan

### New Aggregate: `Delegation`

Within `AuthorizationService.Domain/Aggregates/Delegation/`:

```
Delegation/
├── Delegation.cs              # AggregateRoot
├── DelegationStatus.cs        # Enum: Active, Expired, Revoked
└── DelegationScope.cs         # ValueObject: Permissions, ResourceType, MaxDepth
```

### Delegation Properties

- `Id` — Guid (from Entity base)
- `TenantId` — Guid (from Entity base)
- `DelegatorId` — SubjectId (who grants)
- `DelegateeId` — SubjectId (who receives)
- `GrantedPermissions` — List<string> (specific permissions)
- `ResourceScope` — DelegationScope? (optional resource restriction)
- `Status` — DelegationStatus
- `Reason` — string
- `StartAtUtc` — DateTime
- `ExpiresAtUtc` — DateTime
- `RevokedAtUtc` — DateTime?
- `CreatedAtUtc` — DateTime
- `UpdatedAtUtc` — DateTime

### Invariants

- `ExpiresAtUtc > StartAtUtc`
- `DelegatorId != DelegateeId` (cannot delegate to self)
- Delegated permissions must be subset of delegator's effective permissions
- Status transitions: Active → Expired | Revoked
- Cannot delegate expired/revoke delegation
- Maximum delegation depth: 1 (no delegation chains)

### Domain Events

1. `DelegationCreatedEvent` — DelegationId, DelegatorId, DelegateeId, Permissions
2. `DelegationRevokedEvent` — DelegationId, RevokedBy
3. `DelegationExpiredEvent` — DelegationId (auto-generated by background worker)

### Integration Events

1. `DelegationCreatedV1` — triggers cache invalidation
2. `DelegationRevokedV1` — triggers cache invalidation
3. `DelegationExpiredV1` — triggers cache invalidation

### Background Worker

`DelegationExpirationWorker` — hosted service that:
1. Runs every 5 minutes
2. Queries Active delegations where ExpiresAtUtc < now
3. Marks as Expired
4. Emits `DelegationExpiredEvent`

### API Endpoints

| Method | Route | Purpose |
|--------|-------|---------|
| POST | `/api/v1/authorization/delegations` | Create delegation |
| GET | `/api/v1/authorization/delegations/{id}` | Get delegation |
| GET | `/api/v1/authorization/delegations` | List delegations (by delegator or delegatee) |
| POST | `/api/v1/authorization/delegations/{id}/revoke` | Revoke delegation |
| POST | `/api/v1/authorization/delegations/{id}/approve` | Approve sensitive delegation |

### OPA Integration

Update `AuthorizationServiceClient` to populate `delegated_permissions` in context:

```csharp
// AuthorizationServiceClient.cs
var delegations = await _delegationRepository.GetActiveBySubjectAsync(tenantId, subjectId);
var delegatedPermissions = delegations.SelectMany(d => d.GrantedPermissions);
context.Environment["delegated_permissions"] = string.Join(",", delegatedPermissions);
```

This feeds into existing `AuthorizationDecisionService` Step 5.

---

# Consequences

Positive:

- Leverages existing AuthorizationService infrastructure
- No cross-service data consistency issues
- Step 5 of AuthorizationDecisionService already designed for this
- Simpler deployment (5 services instead of 6)
- Consistent with delegation specification requirements

Negative:

- AuthorizationService becomes larger
- Need to add delegation-specific endpoints
- Background worker adds complexity to AuthorizationService

---

# Migration Path

1. Create `Delegation` aggregate in AuthorizationService.Domain
2. Create repository interface + EF Core implementation
3. Create CQRS features (CreateDelegation, RevokeDelegation, ListDelegations)
4. Create `DelegationExpirationWorker` background service
5. Update `AuthorizationServiceClient` to populate `delegated_permissions`
6. Wire delegation consumer for cache invalidation
7. Add API endpoints
8. Remove Delegation reference from README as separate service
9. Add OPA delegation policy to `opa/policies/delegation/`
