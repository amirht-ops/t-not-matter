## خلاصه مدیریتی

پلتفرم امنیت سازمانی (Enterprise Security Platform) یک معماری متمرکز مبتنی بر سیاست برای مدیریت هویت، مجوزها و خط‌مشی‌ها است. این پلتفرم تصمیمات مجوزدهی را از سرویس‌های کسب‌وکار جدا کرده و به صورت متمرکز ارزیابی می‌کند.

### مدل تصمیم‌گیری

```
آیا موضوع (Subject) می‌تواند عمل (Action) را روی منبع (Resource) در قالب بافت (Context) اجرا کند؟
Decision = Subject + Action + Resource + Context + Policies
```

این مدل از بررسی‌های ساده نقش-مجوز فراتر رفته و از موارد زیر پشتیبانی می‌کند:

- **RBAC دارای محدودیت Tenant** برای تخصیص نقش و مجوز پایه
- **ABAC / مجوزدهی آگاه به بافت** برای ارزیابی ویژگی‌های اجرایی
- **مجوزدهی مبتنی بر مصرف** برای سهمیه و محدودیت نرخ
- **محدودیت‌های وابسته به منبع** برای محدود کردن دسترسی به نمونه خاصی از منبع

### نمونه‌های پشتیبانی شده

- یک سرپرست می‌تواند فاکتورها را حداکثر **۱۰۰ بار در ماه** ایجاد کند
- یک سرپرست می‌تواند فاکتورها را حداکثر **۱ بار در روز** ویرایش کند
- یک سرپرست می‌تواند همان فاکتور را حداکثر **۳ بار در روز** مشاهده کند

## ساختار پلتفرم

### سرویس‌های مرزی (Bounded Contexts)

| سرویس | مسئولیت | تعداد Aggregate | تعداد Domain Event |
|--------|---------|-----------------|-------------------|
| **IdentityService** | احراز هویت: ورود، MFA، نشست‌ها، توکن‌ها | ۲ (User, Session) | ۱۲ |
| **AuthorizationService** | RBAC: نقش‌ها، مجوزها، گروه‌ها، مجوزهای مؤثر | ۶ (Role, Permission, RoleAssignment, PermissionGrant, Department, UsageTracking) | ۲۱ |
| **PolicyService** | ABAC: قوانین پویا، ارزیابی ریسک → همگام‌سازی با OPA | ۲ (Policy, Decision) | ۱۴ |
| **TenantService** | جداسازی و عضویت | ۲ (Tenant, Department) | ۸ |
| **AuditService** | انطباق و ثبت امنیتی غیرقابل تغییر | ۳ (AuditRecord, SecurityEvent, ComplianceEvent) | ۳ |

### فناوری‌های استفاده شده

| فناوری | نقش | مسئول نیست |
|--------|------|-----------|
| Kong | مسیریابی API، محدودیت نرخ، خاتمه TLS | منطق مجوزدهی |
| OPA | ارزیابی خط‌مشی ABAC | مسیریابی، منطق کسب‌وکار |
| Redis | کش کردن مجوزهای مؤثر | منبع حقیقت |
| RabbitMQ | با انتشار رویداد یکپارچه | الگوهای درخواست/پاسخ |
| PostgreSQL | وضعیت پایدار به ازای هر سرویس | دسترسی متقاطع بین سرویس‌ها |
| OpenTelemetry | ردیابی + معیارها + لاگ‌ها | منطق کسب‌وکار |

## آسیب‌پذیری‌های بحرانی

### CRITICAL-01: جریان MFA شکسته
صفحه `/mfa/verify` به JWT نیاز دارد، اما کاربرانی که در حالت MFA قرار دارند هیچ توکنی ندارند. **زمان تخمینی رفع: ۲ روز.**

### CRITICAL-02: آسیب‌پذیری Code Injection در RegoGenerator
مقادیر condition در Rego بدون sanitization درج می‌شوند. **زمان تخمینی رفع: ۱ روز.**

### CRITICAL-03: فقدان اجرای عدم تغییر Audit Log
لاگ‌های audit فاقد مکانیزم append-only، IsSealed یا محدودیت‌های پایگاه داده هستند. **زمان تخمینی رفع: ۳ روز.**
